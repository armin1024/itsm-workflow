# 0.11.0实现对齐与待补充约定

> 本文记录0.11.0历史基线，严格saved确认不再作为当前协议。当前使用HTTP200、整数status=200及data.runId匹配的AopsResult、五阶段单次进度和TERMINATED状态；重试默认最多6次、总等待70秒，提取携带原requestId。现行格式以[回调API文档](tec01-to-itsm-workflow-api.md)及[交付说明](tec01-extraction-execution-alignment.md)为准，其他架构不变。

对齐基线：[方案一修订版](review-delivery/execution-save-then-release.md)。本服务不包含tec01的Java实现；“执行器已实现”不等于tec01已经完成配套。

## 一、已落地

| 事项 | 当前实现 |
|---|---|
| 一次下发、内存连续执行 | 完整Workflow一次传入，后台逐节点执行，不逐节点重新下发 |
| 每步保存确认后再推进 | 运行回调要求严格的已保存确认，未确认不执行下一节点 |
| 同步还是异步 | 下发HTTP请求立即返回受理；后台运行；每个HTTP回调等待tec01保存确认 |
| 不来回传完整执行快照 | 生产回调只有节点事实、结果、分支与运行状态；恢复才传必要状态与前置输出 |
| 有限等待 | 默认每个回调最多总3次请求，单次最多20秒（可配置且封顶30秒），整体最多70秒；仅超时重试 |
| 明确失败停止 | HTTP错误、非保存确认、确认身份不匹配、连接失败均停止；不另起一轮远程“失败通知”重试 |
| 内存生命周期 | SQL完成释放局部CLI名额；计划停止后释放活动任务，不引入SQLite或后台结果补报 |
| 恢复前查旧活动 | 新增受鉴权活动查询，返回当前实例、活动状态、节点和等待阶段；不返回计划、结果或Key |
| 暂停与取消 | 收到控制后在安全边界处理；取消尽力终止CLI，不声明外部回滚 |
| 本地计划确认 | 独立于AOPS Key；确认摘要保存在浏览器，执行时校验摘要与工单、定义、参数一致 |

回调严格确认格式与活动查询示例见两份方向API文档。仅HTTP 200、空data或204不再算运行回调已保存。**tec01必须先配套严格确认，再启用生产同步。**

## 二、已明确的歧义

1. `workflowSnapshot`保留旧API字段名，内容是这次固定的Workflow定义，不意味着每步往返完整运行快照；未为文字命名另造一套接口。
2. tec01创建计划并保存用户确认，执行器负责节点执行与条件判断。调用执行接口不是再次请求LLM规划。
3. `NODE_STARTED`只记录开始，不能证明SQL完成；`NODE_COMPLETED.runStatus`表达该节点结束时可知的运行状态，取消/暂停的竞争仍以实际后续停止事实为准。
4. 保存确认必须在tec01数据库事务提交之后返回。`saved:true`是对端承诺，执行器无法直接证明Java数据库的真实提交；需tec01集成测试验证。
5. 活动查询`active:false`只说明**当前被查询的执行器实例**没有活动任务，不表示SQL没有执行、不表示远端AOPS已经停止，也不证明历史任务成功。
6. 首版部署单服务单进程，systemd固定`--workers 1`。不可在无运行归属控制的情况下多进程或随机负载均衡；否则查错实例可能误判旧活动。
7. 生产执行器退出不保留结果。受理去重只保留有界的标识/哈希/状态摘要，不保存查询数据；进程重启后不承诺历史去重。
8. Studio为浏览器轮询保留短期传输事件，浏览器IndexedDB保存本地知识与计划；这不是生产恢复数据库，也不是结果失败后的后台补报。
9. Studio关闭tec01同步时，不能验证对端数据库保存确认。严格确认由自动化MockTransport测试覆盖，联调需打开同步并使用tec01或同契约测试服务。
10. 恢复不要求重传无关历史，但必须有继续位置、避免重放的状态、分支信息及后续实际使用的前置结果；缺失输入拒绝，不自动补查SQL。
11. 暂停/取消在等待回调确认时不强行冻结HTTP请求，可能等待当前有上限的回调完成或失败；请求受理不等于立即释放。活动查询展示等待阶段与控制标志，tec01应显示请求中。

## 三、tec01必须补齐的职责

- 原回调按运行、调度、节点和执行尝试识别；结果、状态、交互与事件事务保存，重复只处理一次。
- 对旧调度回报可确认已保存历史事实或拒绝，但不能覆盖较新的用户修正、取消状态或后续运行。
- 回调超时后先保留已确认事实；根据节点允许执行时长、回调总等待与通信余量识别中断，不把所有节点统一改为未知。
- 恢复前查询原执行器的活动状态；仍活动则先暂停/取消并等其退出。实例已变或服务不可达时，不能仅凭“查询不到”判定SQL未执行。
- 页面显示请求中与实际生效状态的区别。暂停命令在网络中传输时，执行器可能已经开始下一节点，不承诺点击即冻结。
- 保存用户核实结论、继续位置、必要输入和再次执行确认，才允许新的下发；不依靠透明重试执行接口找回结果。

## 四、仍待双方确认的事项

| 项目 | 本版本处理 / 尚待确认 |
|---|---|
| 业务成功码与确认格式 | 执行器固定HTTP 200、status=200、saved=true并核对身份；tec01需确认与其实际AopsResult一致，不做宽松回退 |
| 迟到回报处理 | 执行器不覆盖tec01数据；Java事务中的旧调度判断、人工修正优先级和重复确认需下游实现 |
| 未知状态多久提示 | 执行器提供活动查询与节点/回调时限；tec01告警检查周期与用户通知方式待业务确认 |
| 整计划总时长与凭据过期 | 已有单节点和回调时限，未新增全计划总时长或凭据自动刷新；是否设置总体执行期限需确认 |
| 累计结果内存限制 | 已有活动计划数、CLI并发、单CLI输出上限；未新增整计划累计结果预算，较大历史结果需限制查询规模并另行确认预算 |
| 多实例扩展 | 本版本只支持固定单进程归属；未来多实例路由和停止证明需单独设计，不宣称现已具备 |
| 提取回调确认 | 本次只收紧运行回调；提取保留原回调/重试策略，若希望统一saved确认需与tec01另行确认 |

不承诺外部SQL严格只执行一次；无数据库时，SQL已执行而回报未保存就崩溃，仍可能丢失结果，用户需依据执行记录核实。

## 五、计划确认问题与修复

原页面的“确认并执行”按钮同时要求勾选计划、填写AOPS Key、满足未知节点核实条件。未填Key时即使勾选也保持灰色，且未说明具体原因，造成无法确认计划的体验。

当前拆为：

1. 核对完整计划，点击“确认此执行计划”，无需Key，不执行SQL。
2. 确认摘要与时间保存在浏览器，刷新后仍可见。
3. 提供本次Key，点击“执行已确认计划”。未满足条件时明确显示阻止原因。
4. 重新计算并核对计划摘要；内容或工单参数变化后，旧确认不能用于新计划。
5. 下发前核实旧活动，避免同一运行并发恢复。

另外修正丢失下发响应的恢复保护：即使节点仍显示READY，只要运行是UNKNOWN，也必须核实后确认，不能据此假定SQL没有执行；明确拒绝时恢复原节点状态，不把未知节点悄悄改成可直接重试。

本地摘要校验防止陈旧确认，不等同于生产用户权限系统。生产审批和planHash仍由tec01负责。
