# 0.13.0 性能验证报告

日期：2026-10-26。此报告区分源码回归、模拟业务测试与真实生产容量，不能将模拟延迟作为AOPS、数据库、模型或内网VM的SLA。

## 1. 测量边界

- HTTP请求通过真实FastAPI ASGI路由，包括鉴权、请求解码、dispatch、活动查询、控制及提取接口。
- SQL使用内存SSE代替CLI，LLM使用短时等待替代推理，tec01使用MockTransport确认；禁止基准主动访问外网、内网业务服务或启动真实CLI。
- 近20MiB场景必须显式添加`--large`，默认不会构造该场景。
- profile名称只选择参数，不会自动改变本机CPU和内存；硬件限额必须由目标VM或容器设置。
- RSS为进程高水位，和应用对象计费不同；本机模拟没有真实CLI进程，所以不代表完整生产进程组的峰值。

## 2. 本机功能与负载观察

一次macOS ARM64、18逻辑CPU环境的4c8g参数模拟，四条普通流程、四条恢复流程、5000条审计、100次提取突发以及单个近20MiB结果均通过。没有施加4核8GiB硬件限额。

|---|---:|
| 健康查询p95 / 最大 | 78.6 / 129.1ms |
| 活动查询p95 | 50.8ms |
| 控制命令受理p95 / 最大 | 34.0 / 113.2ms |
| 事件循环探针延迟p95 / 最大 | 24.7 / 50.7ms |
| 当前进程峰值RSS | 262.2MiB |

健康、活动、控制各27个样本，样本量有限；这是单次观察，不是长期分位数承诺。5000条审计最终去重为一条SQL，检查的是大证据输入而非大最终图。普通/恢复流程各四条均成功，近20MiB结果为单个测试，不代表32个大结果同时执行的容量。

## 3. 重现与内网验收

### 已执行的Linux容器限额验证

另在同一ARM64宿主上以linux/amd64容器仿真执行四档测试，外部明确设置CPU及内存限额，报告中的observedCgroupLimits已读取并核对对应值。脚本hardwareLimitsApplied=false表示脚本本身不设置限额，不能忽略外部实际观测值。

**资源限制说明：Docker VM本身只有18逻辑CPU、约7.75GiB总内存。** 因此配置16GiB/32GiB cgroup上限不意味着实际获得对应内存；这些高档测试只验证参数、控制路径和本次小样本负载，不构成16GiB/32GiB机器容量验收。没有修改宿主或Docker资源配置，也没有尝试耗尽内存。真实高内存档位仍需部署方在相应VM复测。

四档均包含正常、恢复、5000条审计、100次提取突发及单个近20MiB结果；前三档普通流程4条，16c32g档普通流程32条。以下是各自一次运行的观察，不是同硬件、同负载的线性扩容对比。

| 配置的cgroup上限 | 健康p95 | 活动查询p95 | 控制受理p95 | 当前进程峰值RSS | 突发受理 / LLM峰值 |
|---|---:|---:|---:|---:|---:|
| 2 CPU / 4GiB | 30.2ms | 15.8ms | 42.5ms | 274.0MiB | 1 / 1 |
| 4 CPU / 8GiB | 36.7ms | 16.2ms | 54.7ms | 274.1MiB | 1 / 1 |
| 8 CPU / 16GiB | 28.5ms | 27.0ms | 50.5ms | 316.5MiB | 2 / 2 |
| 16 CPU / 32GiB | 29.5ms | 23.7ms | 44.3ms | 296.7MiB | 4 / 4 |

全部检查通过：无外部业务调用、已完成节点不重放、提取并发未越界、测试后预算归还。健康/控制样本分别为68、61、55、76个，均低于本次目标；真实CLI进程组内存目标仍未由此验证。该轮包含解码前容器预检的最终实现。

原始报告：[2c4g](performance-results/2c4g-linux-cgroup.json)、[4c8g](performance-results/4c8g-linux-cgroup.json)、[8c16g](performance-results/8c16g-linux-cgroup.json)、[16c32g](performance-results/16c32g-linux-cgroup.json)。容器限额不等于独占的原生VM，跨架构仿真也不代表生产CPU性能，部署方仍需在真实内网环境复测。

### 自行重现

源码环境：

```bash
uv run --extra dev pytest -q
cd frontend
npm test
npm run build
cd ..
uv run python tools/benchmark_runtime.py --profile 4c8g --scenario all --large --target-p95-ms 250
```

可加`--output output/performance/new-report.json`保存生成报告；父目录须先创建，已有文件会拒绝覆盖，默认只输出到终端。

分别选择2c4g、4c8g、8c16g、16c32g。`--runs`可调整普通模拟流程数；出现429会记录，不靠无限重试掩盖容量限制。

在目标VM运行同一脚本，并另做经授权的真实CLI进程内存测试。若使用等效容器限额，必须同时指定CPU与内存，记录宿主、容器cgroup有效值及是否存在架构仿真。Docker仅用于构建/验收，不是服务的部署要求。

原始报告必须保留measurement中的模拟条件和hardwareLimitsApplied说明。脚本自身不会验证宿主确实拥有profile宣称的资源；不能仅凭改profile就声称做过四种VM压测。

健康/活动查询目标p95≤250ms，暂停取消受理p95≤500ms。超过目标时如实记录，不通过删掉慢样本、放宽确认协议或自动重执行取得好看结果。整组进程的内存目标是有效机器内存70%以内，当前模拟RSS不能验证真实AOPS CLI的额外消耗。

## 4. 回归重点

实现回归：后端175项、前端29项测试通过，前端生产构建通过。后端覆盖请求/证据限额、解码前高密度容器拒绝、任务创建失败、开始前取消、线程取消清理、HTTP池复用、缓存和日志读写竞争；前端使用fake-indexeddb验证迁移及原子事务。

另使用Playwright在隔离测试origin执行浏览器验证，不使用用户实际站点数据：

- v1库包含知识与运行共2条、2500行约4.63MB结果，迁移后为v2四store，知识、计划和完整输出均保留。
- DOM默认100行并可切换200行；完整导出仍为2500行，长字段600字符未被预览截断。
- 人工确认清理后输出删除，知识、运行计划和成功状态保留。
- 在真实浏览器注入QuotaExceededError并拦截假事件接口：6.5秒只请求一次事件，没有dispatch，游标仍0；解除注入后手动恢复，只增加一次事件请求，游标推进至2、结果保存成功，仍没有dispatch。此测试是错误注入，不是填满用户磁盘。
- 页面console没有错误/警告，临时服务和浏览器会话测试后关闭。HITL上下文为兼容仍在对应详情中按需展示，未将其改造成新的独立服务端载荷接口。

- 并发和预算在任务取消、解析异常、回报409/超时及服务退出后正确释放。
- 100次提取突发只在容量范围内启动模型；同请求幂等不重复分析。
- 大JSON真实字节限额覆盖分块传输，超限在业务受理前拒绝。
- 499条候选上限及模型字符预算在LLM调用前检查，错误不误报为LLM分析失败。
- 日志扫描8MiB上限保留，读操作不持写锁；查询中的文件清理仍给出游标失效提示。
- 浏览器迁移失败回滚、摘要分页不读全部输出、结果100/200行预览、配额失败不推进游标和不重放SQL。

## 5. 尚不能据此证明的事项

没有使用生产凭据，没有对真实AOPS、数据库、tec01或LLM网关做压测；不证明其吞吐或故障恢复SLA。真实内网网关时延、数据库并发许可、CLI版本的内存与目标VM长稳测试仍需部署方核验。

tec01回报次数和等待规则未优化：持续故障时提取依然可能较长等待。浏览器/服务临时缓存依然不是持久消息队列；进程重启、过期或长时间离线不能保证未保存结果可找回。

配置选择见[机器容量与参数](machine-sizing.md)，设计边界见[性能优化实现说明](performance-optimization.md)。
