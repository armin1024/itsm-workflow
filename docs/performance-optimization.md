# 0.13.0 性能优化实现说明

本次优化保持单Uvicorn worker、内存执行、tec01生产存储和浏览器调试存储，不引入业务数据库、Redis或新调度服务。生产回报仍逐节点确认，五个提取阶段各一次，TERMINATED、HITL、409停止及原有重试规则不变。

## 1. 并发与预检

- 提取、Studio预览和按工单取证共享提取容量；达到COMPILER_MAX_ACTIVE_JOBS返回429 COMPILER_NO_CAPACITY及Retry-After: 3，不建立无界任务队列。完整证据的相同请求先检查幂等，不重复占用提取名额。按工单ID取证仍需要临时AOPS_API_KEY，不能凭不同证据共享旧请求。
- HTTP按实际接收字节累计，支持没有Content-Length的分块请求。重业务JSON默认64MiB，提取请求及证据默认8MiB。64KiB以上的大JSON接收和准备数不超过CPU_MAX_WORKERS；小请求不因此串行。登录和控制请求最多64KiB。
- JSON解码前先做字符串感知的容器/深度预检，拒绝高展开风险后才构建DOM；解码后再做对象计费。嵌套最多128层、非字符串标量最多4096字节，SQL/text字符串中的括号不当作容器。估算仍不是操作系统硬RSS限制。
- 未鉴权大请求在解码前拒绝。重JSON解码移出事件循环，并保留既有OpenAPI参数和字段校验；超过请求字节上限返回413。
- 审计最多5000条，候选最多499个SQL节点加end；这些校验在模型调用前完成。SQL模板默认最多65536字符，模型输入最多24000字符。模型字符预算不是token预算，网关上下文仍需独立核对。
- 语义和候选超限有独立错误码，不伪装成LLM_ANALYSIS_FAILED；真实模型分析失败继续使用原错误码。

## 2. CPU、内存与取消

SQL解析、Workflow校验、哈希、结果解析、对象计费、复制和回报编码使用有界数据线程池。线程只处理数据，不修改活动运行、事件序号或预算所有权。

CPU_MAX_WORKERS限制实际计算线程。启动CLI前另取得有界的解析接收预留，I/O期间不独占计算线程；结果已到达后才能提交计算的名额也不会无限增加。512MiB/实际计算线程是部署工作空间预留，不是额外分配的数组，也不是操作系统硬内存限制。

取消await不会终止Python线程。代码等待实际future结束后才归还线程/CLI/运行额度，期间同runId仍是活动任务。不会为了恢复而重执行SQL；外部已发出的请求也不保证回滚。

运行受理前预留EXECUTOR_RUN_MEMORY_MB，默认256MiB。恢复输入、输出、诊断及持有数据使用JSON对象树估算计费；单运行超限明确失败，不返回被截断的成功结果。运行已发出的SQL需人工核查后再决定重试。

RUNTIME_DATA_BUDGET_MB同时约束活动数据和临时缓存。提取缓存同时有64条、一小时和COMPILER_CACHE_MAX_MB限制，终态内容单份复用，历史进度仅保留元数据。Studio只保留最新完整快照及64条事件摘要，终态缓存继续遵循15分钟/128条边界，服务重启后不保留。

Studio在启动任务前还预留事件缓存空间，因此同一机器可同时承载的本地大结果调试可能少于纯生产执行。缓存和运行共同占预算，达到字节预算时即使并发槽未满也会拒绝新任务。活动数据不为新请求让路；缓存过期不能被解释为SQL从未执行。

**估算额度不等于RSS上限。** 解码中间对象、分配器、HTTP缓冲、Python基础内存和CLI进程仍消耗内存。预算值以及健康接口dataBudget是应用计费信息，不是物理内存监控。目标机器应观察整个服务进程组并保留至少30%余量。

## 3. HTTP、CLI与日志

- tec01与LLM使用独立、生命周期共享的HTTP池，避免模型请求占满回报连接。测试MockTransport仍独立，不进入生产连接池。
- 同条回报只编码一次，重试复用原字节及幂等键，不额外执行SQL或LLM。
- CLI版本/SHA缓存按绝对路径、设备、inode、mtime_ns、大小区分，变化后重新验证；二进制哈希分块读取。服务启动预检和健康状态不要求每节点重复启动版本进程。
- CLI stdout仍限制20MiB、stderr 1MiB，读取过程中即检查，不到全部读入后才发现超限。
- 日志查询只短暂持写锁获取文件/长度快照，扫描不阻塞日志写入；原8MiB扫描上限、游标过期、专用目录清理及O_NOFOLLOW保留。
- tec01异常时原等待规则不变：提取各阶段仍可能等待完整回报重试。五条进度加终态持续超时，理论附加等待可达约15分钟；本版本没有通过跳过确认缩短等待。

## 4. 浏览器调试数据

IndexedDB v2把摘要、定义/计划和节点结果分开。列表使用摘要索引分页，不读取全部SQL结果；节点点击时按需加载。保存结果、摘要及lastEventId在同一事务提交后再通知相关记录。

旧v1数据逐条游标迁移，失败完整回滚，不删库重建；出现多标签页阻塞时提示关闭旧页。无法迁移时可只读导出旧数据。不要用“清除站点数据”作为迁移失败的默认解决办法。

有活动任务时可见页每2秒轮询、隐藏页每5秒，网络并发最多4；无活动任务不周期扫描。事件环缺号可通过最新快照恢复，但超过临时缓存期限、浏览器休眠或服务重启不能保证找回未保存结果，仍需核查未知状态。

完整结果默认以每页100行展示，可选200行；原始结果不截断并可导出。不会在每次输入或渲染时全量漂亮打印结果。

浏览器结果软预算默认256MiB，同时受浏览器实际配额限制。写入失败明确显示并暂停该任务的自动落盘/拉取重试，不推进游标、不误报同步成功。用户释放空间后手动恢复保存；不自动删除历史数据、不自动执行SQL。手动清理仅针对已成功/已终止运行的输出，知识、计划、摘要及待恢复运行不自动删除。

## 5. 接口与错误兼容

现有生产请求/回报字段不变。新增只读配置performance、健康接口dataBudget/activeExtractions、Schema响应limits和Studio事件historyGap均为附加信息。

| 情况 | HTTP / 错误 |
|---|---|
| 提取容量满 | 429 COMPILER_NO_CAPACITY |
| 大JSON接收名额满 | 429 REQUEST_NO_CAPACITY |
| 全局数据预算不足 | 429 RUNTIME_NO_CAPACITY |
| 请求体过大 | 413 REQUEST_TOO_LARGE |
| 证据超过字节/展开预算 | 413 EVIDENCE_TOO_LARGE |
| 操作数、候选、SQL或模型输入超限 | 422及对应明确错误码 |
| 恢复输入超过运行额度 | 422 RESOURCE_LIMIT，在受理前拒绝 |
| 节点结果超出运行额度 | 节点FAILED，diagnostic.errorCode=RESOURCE_LIMIT，不进入下一节点 |

429带Retry-After: 3。拒绝受理不代表外部SQL已经发出；节点运行中的资源错误则不能当成从未执行。完整恢复JSON仍受64MiB请求上限，超出时应调高相应配置或人工修正恢复资料，不能静默删掉前置结果。
